## 一、三种写法：为什么是「先改库再删缓存」

缓存和数据库要同步，直觉上有三种写法。逐个排除。

### ❌ 写法一：先删缓存，再改库

| 时刻 | 线程 A（写） | 线程 B（读） | 缓存 | 数据库 |
| --- | --- | --- | --- | --- |
| t1 | 删缓存 | | 空 | 100 |
| t2 | | 读缓存未命中 → 读库 | 空 | 100 |
| t3 | | 写回缓存 **100** | **100** | 100 |
| t4 | 改库 → **110** | | 100 ❌ | 110 |

**两个问题，第二个常被忽略：**

1. **窗口大**：从「删缓存」一直拉到「改库提交完成」—— 改库是慢操作（网络 + SQL + 事务提交），窗口是**毫秒级**
2. **缓存空窗期**：这个窗口里缓存一直是空的，**失去了挡请求的作用** —— 所有并发读全部穿透到库，顺带制造一波数据库压力（性质接近缓存击穿）

### ❌ 写法二：先改库，再"更新"缓存

两个写线程各自「改库 + 更新缓存」，**写入缓存的顺序可能与改库顺序相反**：

| 时刻 | 线程 A | 线程 B | 数据库 | 缓存 |
| --- | --- | --- | --- | --- |
| t1 | 改库 → 110 | | 110 | |
| t2 | | 改库 → 120 | 120 | |
| t3 | | 写缓存 **120** | 120 | 120 |
| t4 | 写缓存 **110** ❌ | | 120 | **110** |

**迟到的写入把正确值覆盖成了旧值。**

### ✅ 写法三：先改库，再删缓存

**它也不是绝对安全**，但窗口极窄：

| 失败条件 | 量级 |
| --- | --- |
| 读线程必须**在改库之前**读到旧值 | — |
| 且**慢到跨越整个写操作**才写回 | **微秒级**（读缓存是内存操作） |

**对比结论**：

| | 先删缓存 → 改库 | 先改库 → 删缓存 |
| --- | --- | --- |
| 窗口 | **毫秒级**（整个写操作时长） | **微秒级**（读线程自身耗时） |
| 谁中招 | 窗口内**所有**读请求 | 只有那**一个**被打断的读线程 |
| 额外代价 | 缓存空窗期 → 读全部穿透 | 无 |
| **差距** | — | **2~3 个数量级** |

> **不是"先删缓存会不一致"，而是"它的失败窗口比另一方案大两三个数量级"。**

### 为什么选「删」而不是「更新」

| 理由 | 说明 |
| --- | --- |
| **懒加载，省资源** | 删掉后**只有下次有人读**才重建。改完一直没人读 → 零计算。「更新」是不管有没有人读都得算一遍写一遍 |
| **幂等，并发安全** | 删两次结果一样；「更新」会因**写入顺序颠倒**留下旧值（写法二的失败模式） |
| **不会漏字段** | 删掉后重新查库拿到的必然是与库一致的完整对象；「更新」要手工组装，嵌套结构（如 `Dish` 带 flavors）容易漏 |

> **一句话**：缓存的正确姿势是**懒的** —— 写操作只负责「**宣告我脏了**」（删），不负责「立刻变干净」（更新）。
>
> ⚠️ **但要注意边界**：删除「**不引入错误**」（幂等、不会写错值），**不等于「保证正确」** —— 它挡不住读线程把旧值写回来。这正是延迟双删存在的前提。

## 二、它仍然不是强一致：两个真实的 gap

### gap 1：微秒级窗口（前面已述）

需要读线程被打断着跨越整个写操作，概率极低。

### gap 2：🔴 事务提交时机（项目里真实存在）

看 `DishServiceImpl` 的三个写方法：

```java
@Transactional
public int updateDish(Dish dish) {
    int rows = dishMapper.updateDish(dish);       // ① 改库（事务内，未提交）
    redisCache.deleteObject(DISH_ONSALE_KEY);      // ② 删缓存 ← 在提交【之前】就执行了
    clearDishCache(dish.getId());                  // ③ 同上
    return rows;
}                                                  // ④ 方法返回，事务才由 AOP 提交
```

**问题**：② ③ 发生在事务提交**之前**。而事务提交是 Spring AOP 在方法返回后才做的。

| 时刻 | 线程 A（写，事务中） | 线程 B（读） | 数据库 | 缓存 |
| --- | --- | --- | --- | --- |
| t1 | 改库 → 110（**未提交**） | | A 眼中 110 / B 眼中 100 | 有 100 |
| t2 | **删缓存** | | | 空 |
| t3 | | 读缓存未命中 → 读库 → **读到 100**（A 未提交，B 看不到） | | |
| t4 | | 把 **100** 写回缓存 | | **100** ❌ |
| t5 | 方法返回，**事务提交** | | **110** | 100 |

**反差感在于**：**隔离性本来是用来"保护"的，这里反而制造了窗口** —— 正因为 B 看不到 A 未提交的修改，B 才名正言顺地读到旧值并回填。窗口大小 = **整个事务执行时长**（毫秒级），比 gap 1 大 3 个数量级。

**修法：把删缓存挪到事务提交之后。**

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        redisCache.deleteObject(RedisKeys.DISH_ONSALE_KEY);
        clearDishCache(dish.getId());
    }
});
```

三种常见做法：① `TransactionSynchronizationManager` 注册回调（推荐）② 拆成"事务方法 + 缓存方法"两个方法
③ `@TransactionalEventListener(phase = AFTER_COMMIT)`。

> **处置状态**：**知道但暂不改**。当前并发低、窗口为毫秒级，属"技术判断"而非"隐患"。
> 另注：菜品缓存 TTL 是 **1800 秒**，一旦脏要脏 30 分钟 —— 这个比 gap 更值得审视。

## 三、延迟双删

### 它防的是什么：主从复制延迟

**不是**「读线程慢」，而是**读写分离下的从库同步延迟**：

| 时刻 | 事件 | 主库 | 从库 | 缓存 |
| --- | --- | --- | --- | --- |
| t1 | 写线程改主库 | 110 | 100（未同步） | 100 |
| t2 | 删缓存 | 110 | 100 | 空 |
| t3 | 读线程走从库 → 拿到 **100** | 110 | 100 | 空 |
| t4 | 回填缓存 → **100** | 110 | 100 | **100** ❌ |

**关键区别**：这次读线程**没有变慢** —— 它正常速度执行，问题在于「它读的是从库」。

| 失败场景 | 窗口 | 依赖因素 |
| --- | --- | --- |
| 读线程被打断 | 微秒级 | 线程调度、GC |
| **主从复制延迟** | **100ms ~ 数秒** | 网络、从库负载 |

**差 5~6 个数量级** —— 这才是延迟双删要防的东西。

### 做法

```
改库 → 删缓存① → 等待 Δt → 删缓存②
```

**为什么要「延迟」**：脏值的回填**必然发生在删缓存①之后**。如果第二次删紧贴着第一次（间隔 0），脏值还没回填，**删了个寂寞**。必须隔一段时间，让「读到旧值 → 回填」这个动作先发生完，再删。

**延迟窗口要覆盖的，正是"脏值可能被回填的时间"。**

### 为什么它仍然不能保证一致

**① 延迟时长无法确定**（死穴）

| 延迟太短 | 延迟太长 |
| --- | --- |
| 第二次删跑在脏值回填**之前** → **白删** | 这段时间缓存**一直是脏的** → 期间所有读都读到旧值 |

而延迟该多长取决于**主从复制延迟**（网络、从库负载，波动）和**读线程自身耗时**（不可测）—— 两个变量都测不准，只能拍一个经验值（常见 500ms~1s）。

**② 第二次删本身也可能失败**（Redis 抖动）→ 脏值留到 TTL 过期 → 还得配失败重试。

**③ 不能用 `Thread.sleep`** —— 会占住请求线程，必须另起异步任务或延时队列。

> **结论**：延迟双删是**概率优化**，TTL 才是**正确性兜底**。
> 无论中间多脏，TTL 到了就自动纠正 —— **所有缓存一致性方案都必须配 TTL。**

### 什么时候该用 / 不该用

| 该用 | 不该用 |
| --- | --- |
| 读写分离 + 主从延迟明显 + 对短时不一致敏感 | **单库**（无主从 → 主从延迟场景不存在 → 纯属过度设计）<br>缓存 TTL 很短（脏值最多活几十秒，收益有限） |

> **本项目的判断**：库是**单库**（`localhost:3306/ry-vue`，无主从）→ **延迟双删防不住任何东西，不做**。
> 真正值得改的是第二节的 `afterCommit` gap。

## 四、Lua 脚本原子性

### 为什么需要：多条命令之间的「空档」

**Redis 的单条命令是原子的**，问题出在**多条命令之间** —— 那个间隙里别的客户端可以插进来。

### 最经典的场景：释放分布式锁

**不用 Lua（错误示范）**：

```java
String token = stringRedisTemplate.opsForValue().get(lockKey);
if (myToken.equals(token)) {                  // ← 空档从这里开始
    stringRedisTemplate.delete(lockKey);      // ← 到这里结束
}
```

这个空档可能横跨几十毫秒。若锁在此期间到期自动释放、被别的线程拿走并写入自己的 token，你的 `delete` 就删掉了**别人的锁** —— 互斥彻底失效。

**用 Lua（正确）**：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**「比对 + 删除」被塞进 Redis 内部一次执行完，中间不可能插进任何命令。**

| 片段 | 含义 |
| --- | --- |
| `redis.call(...)` | 在脚本里调用 Redis 命令 —— 是 **Redis 内部**在调，不是 Java 在调 |
| `KEYS[1]` / `ARGV[1]` | 第 1 个 key / 第 1 个普通参数，**都是 1-based** |
| 相等 → `return 1` | 锁是我的，已删 |
| 不等 → `return 0` | **不是我的锁，什么都没做** |

### 你其实一直在用 Lua：Redisson 的 unlock

```lua
if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then return nil end
local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1)
if (counter > 0) then
    redis.call('pexpire', KEYS[1], ARGV[2])     -- 还有重入，续期后返回
    return 0
else
    redis.call('del', KEYS[1])                  -- 计数归零，真正删锁
    redis.call('publish', KEYS[2], ARGV[1])     -- 通知等待者（不是轮询）
    return 1
end
```

| 细节 | 说明 |
| --- | --- |
| 用 **Hash** 而不是 String | field 存 `UUID:threadId`，value 存**重入计数** → 这就是**可重入锁**的实现 |
| `hincrby -1` 而不是直接 `del` | 重入几次要解锁几次，计数减到 0 才真正释放 |
| `publish` 而不是让等待者轮询 | 解锁时主动广播，`subscribe` 的客户端被唤醒 |

> ⚠️ **容易误解的点**：`isHeldByCurrentThread()` 查的是 **JVM 本地 map**，不是 Redis。
> 它只挡「别的线程来解锁」，**挡不住「锁已过期、被别的客户端拿到」** —— 后者靠 Lua 里的 `hexists` 挡。

### 为什么单线程就能保证原子

| 问题 | 答案 |
| --- | --- |
| Redis 是单线程吗 | **命令执行是单线程**（IO 自 6.0 起多线程，**执行命令仍单线程**） |
| 脚本怎么执行 | Lua 脚本被当成**一条命令**提交，天然继承「一次只跑一条命令」的性质 |

### 代价

| 代价 | 说明 |
| --- | --- |
| **阻塞整个 Redis** | 脚本期间其他所有请求排队。`lua-time-limit` **默认 5 秒**，超时后其他请求收到 `BUSY`，**但 Redis 不会杀掉脚本** |
| **脚本必须短** | 必须 O(1) 级，**绝不能遍历大集合**（`KEYS *`、大 Hash 循环） |
| **集群下多 key 同 slot** | 否则报 `CROSSSLOT`，需用 hash tag（`{lock}:a`） |

### ⚠️ 原子性 ≠ 事务

**Redis Lua 的"原子"指「不可打断 + 隔离」，不是「要么全成功要么全失败」。**

| | 含义 | 有回滚吗 |
| --- | --- | --- |
| **ACID 的 A**（MySQL 事务） | 要么全成功、要么全失败 | ✅ rollback |
| **Redis Lua 的"原子"** | 整段不被其他命令插入 | ❌ **没有回滚** |

**后果**：脚本中途报错，前面已执行的命令**不会撤销**。所以**脚本设计上要保证中间不会出错**（如别对 String key 调 `lpush`）。

**注**：Redis 的 `MULTI/EXEC` 同样**不回滚**。

## 五、手写锁 Demo（已实现并验收）

### 三个文件

| 文件 | 内容 |
| --- | --- |
| `sky-merchant/.../lock/SimpleRedisLock.java` | 手写 SET NX PX 锁：`tryLock` / `unlock` / `newToken` / `peekHolder` |
| `sky-merchant/.../controller/LockDemoController.java` | `/merchant/lockdemo/acquire`、`/release` |
| `sky-merchant/.../constant/RedisKeys.java` | 新增 `LOCK_DEMO_PREFIX = "merchant:lock:demo:"` |

### 三个设计决定

1. **加锁用 `SET key token NX PX ttl`，不用老的 `SETNX` + `EXPIRE`**
   后者两条命令之间有空档，进程在中间挂掉则 key 永不过期 = **死锁**。
2. **解锁走 Lua，不写成「先 get 比对、再 delete」两步** —— 见第四节。
3. **token 做成方法参数，不做成员变量**
   本类是单例 Bean，成员变量会被所有线程共用 → 任何线程都能比对通过 → **防误删形同虚设**。

### 刻意留的缺口

**不做看门狗续期** —— 续期不是锁的必需品，是 Redisson 为「业务没跑完锁就到期」额外加的一层。
先跑通裸锁，才能理解那一层在补什么。另留 `peekHolder()` 便于观察锁到期。

### 验收五步（实测通过）

| # | 命令 | 返回 | 验证 |
| --- | --- | --- | --- |
| 1 | `acquire?key=A&token=t1` | `locked=true, holder=t1` | 抢到锁 |
| 2 | `acquire?key=A&token=t2` | `locked=false, holder=t1` | **互斥** |
| 3 | `release?key=A&token=t2` | **`released=false, holder=t1`** | **★ 防误删** |
| 4 | `release?key=A&token=t1` | `released=true, holder=null` | 正常释放 |
| 5 | `acquire?key=A&token=t2` | `locked=true, holder=t2` | 锁可重新获取 |

**第 3 步是关键证据**：`released=false` 而 `holder` **仍是 `t1`** —— 说明 t2 这一刀**什么都没删掉**，
正是 Lua 里 `token` 比对不过、走 `else return 0` 的效果。

**追加观察**：用 `ttl=3000` 加锁后等 5 秒再释放 → `released=false` 且 `holder=null`
—— 这就是**锁到期自动释放**，也是 Redisson 要加看门狗的原因。

## 六、Lua 做不到什么（防滥用）

> **Lua 只能保证「多条 Redis 命令之间」的原子性。跨 Redis 和 MySQL 的，它管不了。**

### 本项目：「扣库存 + 清缓存」不能用 Lua

```
扣库存  →  MySQL 事务
清缓存  →  Redis 命令
```

两件事分属两个系统，Lua 无法绑成一个原子单元。

**正确解法**（Day11 已实践）：

```
扣库存  →  带条件的原子 UPDATE（WHERE stock >= n），数据库行锁保证原子
清缓存  →  放到【事务提交之后】（afterCommit 回调）
兜底    →  TTL
```

**为什么这样就够了**：因为**这两件事本来就不需要原子**。
只要保证「缓存删除发生在库存真实生效之后」即可 —— 中间滞后几十毫秒，读到的只是旧库存，
而**真正的约束由数据库把守**，缓存只是展示层，允许短暂陈旧。下单时会再走一次 `WHERE stock >= n` 校验。

### 对照：Lua 什么时候才是对的工具

| 场景 | 库存放在哪 | 该用什么 |
| --- | --- | --- |
| 本项目 | MySQL | 条件 UPDATE + afterCommit |
| 秒杀 / 预扣库存 | **Redis** | ✅ **Lua 是正解** —— 判断 + 扣减一次完成 |

**不是「Lua 没用」，是「用错地方」。**

## 七、一致性方案总表（含强度维度）

| 方案 | 一致性强度 | 代价 | 适用 |
| --- | --- | --- | --- |
| **① 先改库 → 删缓存 + TTL 兜底** | 最终一致（脏值 ≤ 一个 TTL） | **最低**：0 额外组件；窗口小但存在 | **绝大多数场景的默认** |
| **② 延迟双删** | 降概率，仍不保证 | 需异步/延时任务；**延迟时长只能拍脑袋** | 读写分离 + 主从延迟明显 |
| **③ MQ 异步删 + 消费重试** | 高可靠（可做到最终一致） | 引入 MQ + **消费幂等** + 积压监控 | 对一致性要求高的中大系统 |
| ④ 订阅 binlog（Canal） | 最高 | 基础设施最重 | 大型系统 |
| ⚠️ **分布式锁（读写都串行化）** | 强一致 | **吞吐骤降**（Day11 实测 0.04s → 0.46s，差一个数量级）+ 锁管理复杂度 | 冲突极少但要求强一致 |

**三个方案的关键差异不只在代价，更在「能保证到什么程度」。**

## 八、概念防混淆表

| 概念 | 一句话 | 出现在哪 |
| --- | --- | --- |
| **更新丢失**（Lost Update） | 两个写互相覆盖，后写的抹掉先写的 | Day11 的 V0 裸写扣库存（超卖 17 份） |
| **ABA** | 值 A→B→A 绕回来，CAS 误判「没人动过」 | 无锁数据结构（**与缓存一致性无关**） |
| **缓存旧值回填** | 读在写**之前**拿到旧值，在写**之后**才写回 | 缓存一致性 —— 延迟双删要防的就是它 |

⚠️ **别把「旧值回填」叫成 ABA** —— 后者需要"A→B→A 绕回原样"这个前提，成因完全不同。

## 九、面试话术

**问「怎么保证缓存一致性」**：

> 「默认是**先改库再删缓存 + TTL 兜底**，做到最终一致，代价最低。
> 注意是"删"不是"更新" —— 删是幂等的、不会写错值，更新会因写入顺序颠倒留旧值。
> 如果读写分离、主从延迟明显，再叠**延迟双删**降低不一致概率 —— 但它**不保证**，因为延迟时长没法确定。
> 对一致性要求更高就上 **MQ 异步删 + 重试**，代价是引入 MQ 和幂等处理。
> 至于**分布式锁**，它能把一致性做到最强，但会让读也排队 —— 我实测过吞吐差一个数量级，所以只在冲突极少时才考虑。」

**问「Lua 为什么能保证原子性」**：

> 「Redis 执行命令是单线程的，而 Lua 脚本被当成**一条命令**提交 —— 所以脚本一跑起来会一口气执行完，
> 期间不处理任何其他客户端命令。
> 代价是**阻塞整个 Redis**：`lua-time-limit` 默认 5 秒，超时后其他请求收到 BUSY 但脚本不会被杀，
> 所以脚本必须是 O(1)，不能遍历大集合；集群下多 key 还得同 slot。
> 另外要注意 —— 这里的"原子"是**不可打断**，**不是"能回滚"**。」

**问「扣库存 + 清缓存能用 Lua 保证原子吗」**：

> 「不能。Lua 只能保证多条 **Redis 命令**之间的原子性，而扣库存在 MySQL、清缓存在 Redis，跨系统。
> 而且这个需求**本来就不需要原子** —— 只要保证"缓存删除发生在库存生效之后"，用 afterCommit 回调就行。
> 真正的约束由数据库的 `WHERE stock >= n` 把守，缓存只是展示层，允许短暂陈旧。
> 如果库存本身放在 Redis（比如秒杀预扣），那 Lua 就是正解。」
