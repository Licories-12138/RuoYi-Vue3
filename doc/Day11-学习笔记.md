## 一、今天最有价值的一句话，是我自己说出来的

我在看到 V3 的实验数据后说了这么一段：

> 「这个场景其实不该用版本号 CAS。版本号乐观锁的价值在'冲突少'；你现在恰恰是'同一行高频冲突'，它必然牺牲大量请求。而'扣库存'这件事，根本不需要版本号 —— 把库存够不够直接写进 UPDATE 条件就够了。」

**这句话是整个 Day11 的结论。** 我不是在背概念，是从数据里推出来的，这条最值钱。

推的过程：

1. 先看 V0 —— 超卖 17 份，确认"不加控制必然坏"
2. 再看 V3 的数据 —— **5 并发居然失败 2 个**，这超出了我的预期
3. 去想为什么 —— 发现是"零退避的自旋式重试"在极端同发下等于没重试
4. 加了退避之后 100% 成功 —— 但耗时翻倍了
5. 然后想到更根本的问题：**为什么非要重试？**
6. 因为 `version = ?` 引入了一个跟业务无关的约束 —— "你读到的快照必须没过时"
7. 但业务真正关心的只有"库存够不够"
8. 那 `stock >= n` 就够了，version 是多此一举

**第 5 步是关键跳跃。** 前三步都在"优化重试机制"，第 5 步跳出来问"为什么需要重试"。这就是从"调参"到"质疑方案本身"的转变。

## 二、我一开始想错的地方

### 想错 1：以为"少卖 17 份"

跑完 V0 我第一反应是"V0 不应该是少卖了 17 份吗"。

**错在把两个量搞混了**：

- **库存少扣了** 17 份 ✅
- **用户少卖了** 17 份 ❌

实际上 20 个用户**全都**被告知成功了，一份没少卖。是**账面只扣了 3**。准确说法是"**卖超了 17 份**"（答应了 20 份，账面只有 3 份的扣减）。

**记住**：超卖量 = 成功请求数 − 库存实际减少。它衡量的是"答应了却扣不到的份数"。

### 想错 2：SQL 写成了绝对赋值

我的 V3 第一版 XML 写的是：

```sql
set stock = #{stock}
```

我以为传进去的是"扣完之后的库存"，但实际上我在 Java 里传的是 `dish.getStock()` —— **我读到的那个值本身**。所以这条 SQL 的含义变成了"把库存设回我读到的值"，等于没扣。

当时的实测形态很魔幻：20 个请求全"成功"，版本号涨了 5（只有 5 次 CAS 成功），但库存基本没掉。**这就是"绝对赋值 + 并发写"的典型指纹**。

**记牢**：

```
等号右边是 stock 自己（stock = stock - n）  → 扣减 ✅
等号右边是纯参数     （stock = #{stock}）    → 覆盖 ❌
```

这条要变成条件反射。

### 想错 3：以为 20 并发是"小压力"

我一直觉得 20 并发很小，所以预期 V3 应该 20/20 全过。结果无退避版本只过了 6 个。

**原因是时间尺度，不是压力大小。** 用 `threading.Barrier` 放出的 20 个请求，是在同一微秒内冲进来的。3 次重试背靠背执行，全部在 0.2 毫秒内打完 —— 这个窗口太短，短到所有竞争者永远在同一时刻碰撞。

**教训**：描述并发压力不能只看"多少个请求"，还要看"它们多密集"。`Barrier` 制造的瞬时同发，是理论上的最坏情况。

## 三、今天踩的五个坑

| # | 坑 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | Redisson 启动失败 | `application.yml` 里 `password:` 留空 → 发 `AUTH ""` 被拒 | 注释掉那行 |
| 2 | XML 改了没生效 | `resources` 下的 XML 要 clean 重编译才打进 target | `mvn clean package` |
| 3 | 脚本虚报成功 | 若依对 `ServiceException` 也返 HTTP 200，脚本只看了状态码 | 改判 body 的 `code == 200` |
| 4 | V1 返回影响行数 | MyBatis 的 update 返回的是行数，不是业务值 | `return current - count` |
| 5 | 无退避重试 | 3 次背靠背 = 实际只试 1 次 | `Thread.sleep(10L * i)` |

### 坑 1 的复盘（最值得记）

Redisson 报 `Unable to connect to Redis server`，我第一反应是"Redis 3.2.100 太老，不支持 `HELLO` 命令"，直接推动升级到 8.10.2 —— 折腾了下载、镜像、配置。

**升级完还是失败。** 拿到完整堆栈才发现真因是 `password:` 空值。

**这里我的思维错误是**：看到一个"合理"的解释就停止追查。`Unable to connect` 确实和 Redis 有关，版本老也确实是个问题（但不是这个问题的因），于是我就锁定了结论。

**应该做的**：先要完整堆栈，再下判断。堆栈里其实写得很清楚（`AUTH called without any password configured`），我早该看一眼。

**这条要写进习惯**：现象 → **完整证据** → 假设，不是 现象 → 假设 → 找证据。

### 坑 3 的复盘

脚本报"成功 20 个"，而日志里明明有 16 条 "系统繁忙"。**数据自相矛盾时，先信日志。**

若依的 `GlobalExceptionHandler` 对业务异常返回 HTTP 200（code 在 body 里），这导致按状态码统计全部失真。

**通用教训**：**HTTP 200 ≠ 业务成功。** 所有统计都要看业务码。

## 四、V3 到底学到了什么

V3 的实验"没跑出漂亮的 100%"，但它是最有价值的一版 —— 因为它**失败过**。

**V3 的正确用法**（不是扣库存）：

- 用户编辑自己的资料 → `version = ?` 防止 A 覆盖 B 的修改
- 后台管理改表单 → "数据已被他人修改，请刷新"
- 读多写少的配置表

**共同点**：冲突偶发，撞上了让用户重试一次可以接受。

**V3 不该用于**：单行热点写（扣库存、秒杀、计数器）→ 冲突是常态，让 70% 用户重试是灾难。

**一句话总结 V3**：

> 乐观锁不是"更高级的锁"，它是一次**押注** —— 赌冲突不会发生。赌赢了零开销，赌输了重试。**押注适合低风险牌桌，不适合人挤人的赌场。**

## 五、四版的直觉记忆

| 版本 | 一句话直觉 |
| --- | --- |
| V0 | "我读一下、算一下、写一下" —— 三个人同时做，后写的把先写的抹了 |
| V1 | "排队，一个一个来" —— 稳，但队太长，还要请个保安（Redis） |
| V2 | "别读了，直接把条件写进 SQL" —— 让数据库自己保证原子性 |
| V3 | "我先记个版本号，写的时候对一下暗号" —— 对不上就重来 |

**选型口诀**：

```
能一条 UPDATE 解决 → V2（条件更新）
必须跨行/跨表/跨服务 → V1（分布式锁）
读多写少、冲突偶发 → V3（乐观锁）
```

## 六、面试要能讲出来的三句话

1. **"扣库存用乐观锁是错的。"**  
   理由：乐观锁的价值在"冲突少"，扣库存是"同一行高频冲突"，必然牺牲大量请求。实测 20 并发下无退避版本成功率只有 30%。

2. **"正确做法是把业务约束写进 WHERE。"**  
   `UPDATE ... SET stock = stock - n WHERE stock >= n` —— 让数据库的行锁串行化，一次成功、零重试、零额外依赖。

3. **"乐观锁如果要用，重试必须带退避。"**  
   我实测过零退避的自旋式重试，3 次重试在 0.2 毫秒内打完，等于没重试；加 10ms 递增退避后成功率从 30% 拉到 100%，代价是耗时翻倍。

**再加一句加分**：

> "而且我做过单实例的极限压测（`Barrier` 同瞬间放出），知道这个 100% 是本地环境的数 —— 生产跨实例、有网络抖动，冲突窗口会放大。所以我的结论是机制层面的，不是宣称 20 并发没压力。"

**这句体现的是"我知道我的实验边界在哪"**，比堆砌数字强。
